HelloNotes — UI layout wireframes

The layout contract, drawn per device. Plates are true to internal proportion; regions carry their real size in points. Approve these and the contract is fixed — the headless harness then proves it before any app code changes.

Layout follows the axis of abundance, not the width alone. Wide displays have horizontal room, so navigation becomes side rails — library left, inspector right. Tall displays have vertical room, so navigation becomes a band across the top and the editor keeps the full measure beneath it. Phones have neither, so the editor is the whole screen and everything else retracts. In all three, the reading column is protected and the way to switch notes never disappears.

Why aspect, not width. An iPad in portrait is 834pt wide — by width alone that buys a second column and a 554pt measure. Band it instead and the editor gets the full 700pt measure with navigation spending the height that portrait has to spare. Same pixels, better reading.

The inspector consolidates four surfaces that are scattered today — references panel under the note, outline in a popover, tags in the left sidebar, graph in a separate window. On a wide display they become tabs in one rail; below 1400pt they collapse back to on-demand popovers and the Graph window. Selecting a tag still filters the note list on the left — the rails cooperate.

The left rail is a switcher, not a list: commands are not places, and bookmarks and recents span collections while a list beside them shows one. Those live in the Library place, which occupies the note-list column when the rail is on Library. Because the rail names the collection, it replaces the note list's collection level — the tree roots at that collection's folders. Group rows survive only in search, which is cross-collection and still has to say where each hit came from.

3 · Reading is not editing · the same note, two different demands

Intent tracks the device. Someone at a 3840pt display is editing — building tables, drafting Mermaid diagrams, restructuring. Someone holding an iPad is almost certainly reading. The measure cap serves reading; it must not become a cage for editing.

IntentTypical contextProseBlocks — tables, code, Mermaid, math, imagesTools
ReadingiPad, phone, Reading modefixed 80ch · centredfit to pane, scroll if widernone — mode switcher only
EditingMac, large windows, Edit / Source / Splitfull pane · left-alignedfull pane widthalways within reach

The constraint belongs to reading, not editing. A fixed 80ch column inside a 3200pt pane is 17% of the display — and since splitting is manual, that is the default state of a wide window, not an edge case. Nobody would accept a Markdown file rendered as a ribbon down the middle of a code editor. Think VS Code: editing runs full width, left-aligned, from the left gutter to the pane edge. Reading keeps the centred measure, because reading is the activity where line length decides comfort.

4 · Modes and the wrap ruler · reading · editing · source

The cap becomes a ruler. Rather than one hard maximum, prose wraps at a configurable ruler — the print-margin guide every developer already knows from Xcode and VS Code, measured in characters so it tracks text size. Blocks break the ruler; nothing breaks the pane.

Two settings, because they are two activities. Appearance ▸ Reading width — Narrow 60 · Normal 75 · Wide 90 · Full. Appearance ▸ Wrap ruler — 72 · 80 · 100 · Off, with an optional guide line. Set them equal and switching modes never reflows; leave them apart and reading gets the tighter measure it deserves while editing keeps the room it needs.

Implications worth stating, because they bite: (a) the ruler is a maximum, not a minimum — effectiveWrap = min(ruler, pane − insets), so a narrow pane simply wraps earlier and a phone never sees the setting at all; (b) blocks break the ruler but never the pane — anything wider scrolls inside its own container, so the page never scrolls sideways; (c) the ruler is global, not per pane, so two panes each wrap at min(ruler, own width) and stay visually consistent; (d) Split shows both settings at once, side by side — the clearest demonstration that they are different activities.

8 · Compact — the editor is the screen · Apple Music model

The open note behaves like the now-playing track. A bottom tab bar carries the app’s places — Notes, Search, Tags, AI. The note you are editing persists above it as a mini strip, one tap from full screen, exactly as a mini-player does. Both retract as you scroll or type and return when you scroll back, so writing gets the entire display without losing your way back.

10 · Decisions needed · these change what you see daily

1 · Right inspector absorbs backlinks, outline, tags and graph into one tabbed rail at ≥1400pt. That moves tags out of the left sidebar — the biggest visible change.
2 · Tall shells band navigation across the top instead of using a second column.
3 · Compact adopts the Apple Music model — bottom tab bar plus a retracting mini-note strip.
4 · Two columns at the 860pt Mac minimum rather than today’s always-three.
5 · One shell replaces MacContentView + iOSContentView.
6 · Panes default to 2 at ≥1400pt of detail — or should splitting always be manual?
7 · Two width settings — Reading width (default 75ch) and Wrap ruler (default 80ch), both in characters so they track text size. Equal values mean mode switching never reflows.
8 · Blocks break the ruler, never the pane — tables, Mermaid, code, math and images fill the pane and scroll inside themselves if wider.
9 · Format bar is per pane and persistent with a pointer, and becomes the keyboard accessory bar under touch.
